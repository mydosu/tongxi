# 同席协作重构方案（v0.3，2026-10-22）

依据 [协作模式讨论.md](协作模式讨论.md) 第 1–8 轮的结论。v0.1 是没问清需求前写的，已作废。

## 1. 要解决的问题（用户原话归纳）

- 行为难预测、乌龙多、费额度。
- 协作里满眼「未验证、未构建、遗留」，成员被一堆「不要 xxx」限制，正常的活也做不完。
- 插话要等下一轮才到主脑，没法及时指引方向。
- 最心疼：同一个问题在「排查 → 修复 → 遗留 → 再排查」里打转。
- 功能多到说不清。

## 2. 目标

同席只做一件事：**主脑按需求把活分给能力相当的成员，强模型不干杂活；前提是一件事能像在单个对话里一样做完。**

验收看这几条：

| 目标 | 怎么量 |
|---|---|
| 做得完 | 一件事结束时，主脑交给用户的是「做完了」或「需要你定 X」，不是一串遗留；同一问题不出现第二次「派人从头排查」 |
| 插话即时 | 用户发给主脑的话，在主脑当前这一步结束前就被它看到（不等回合） |
| 分活合理 | 跑测试、构建、查日志、批量改这类活，落在模型档案里「便宜」档的成员上 |
| 省额度 | 主脑花费明显低于现在调度的每周 $77（同等工作量），具体数在第 1 期实测后定 |
| 好懂 | 功能能用一段话讲清：开主脑、跟它说、它分活、它做完 |

## 3. 新架构

### 3.1 主脑
- **一个项目只有一个主脑。** 主脑是项目里的原生 CLI 会话（和成员私聊用的是同一套），工作目录是项目根目录。它带着上下文对手上这件事负责到做完。不同项目的主脑各自独立，可以同时跑。
- **事一件一件做。** 主脑同一时间只推进一件事；做这件事时可以同时派几个成员。你中途提的新事排在后面，做完当前这件再接；想先做新的，跟主脑说一声，它把当前的停在稳妥的地方、记进任务书再换。
- **长难的活先写任务书。** 主脑判断一件事长或难时，先写任务书 `.tongxi/任务书/<事名>.md`：目标、拆成哪几步、每步派给谁（什么档的模型）、怎样算做完。边做边在任务书上勾进度、记关键结论。短小的事不写。
- **模型：** 项目设置里有一个默认主脑模型，可以改。
- **界面：** 主脑是一个独立对话，像私聊一样点进去说话；项目群里只显示汇总（开始做什么、派了谁、做完、要你定的事）。
- **插话：** 你在主脑对话里说的话直接进它的会话；它正在干活时当插话塞进去（复用现有给会话插话的通道）。
- **会话寿命：** 一件事一个主脑会话。做完时把要长期记住的写进 `.tongxi/计划.md`，会话结束；下一件事开新会话，读计划接着做。一件事中途上下文太大就压缩，或开新会话读任务书接着做。

### 3.2 主脑的工具（同席通过 MCP 提供）
只有这几样：
1. **派活**：指定成员、模型、档位、要做什么、要交回什么。异步：派完立即返回，主脑可以同时派几个人、自己接着干。每个成员在自己的工作树里做。
2. **成员动态**：看某个成员在干什么；给它插话；叫它停。
3. **问用户**：挂到问答面板，用角标提醒，不打断。
4. **查额度**：各账号剩余额度、其他项目的主脑正在用哪些成员。只给主脑看，界面不显示。

成员做完，同席把它的交付（摘要、分支、改了哪些文件）作为一条新消息送进主脑会话。主脑自己判断够不够：不够就对**同一个成员、同一个会话**接着说，而不是记遗留、再派新人。

合并：主脑自己在项目根目录用 git 合并成员分支、处理冲突，不再由同席代合并。

### 3.3 模型档案（取代价格表、用量、额度显示）
- 一个短文件，每个模型一行：能力档（强 / 中 / 弱）、贵贱档（贵 / 中 / 便宜）、擅长、注意点。
- 初稿由同席从现有模型目录生成，之后用户可以直接改；不做自动抓价格。
- 主脑开会话时就带着它。分活原则只有一条：贵的模型想、判断、收口；便宜的模型干体力活。

### 3.4 成员说明
只留最少的：在哪个目录工作、做完交回什么、别泄露密钥、有改生产授权时直接在生产上测（先备份）。不列禁区，不分遗留档。

### 3.5 保留 / 删除

| 保留 | 删除 |
|---|---|
| 成员私聊、多开席位、成员原生会话 | 回合制调度（每回合新开调度、账本、路由表） |
| 问答面板 | 拨款请求、请教模式、当场重派、空跑判定、空分派放行 |
| 长期计划文件；新增任务书 | 遗留池与遗留分档、验证门、hold_merge、软预算 |
| 工作树隔离 | 价格表与自动更新、用量统计、额度显示 |
| 模型目录（生成档案用） | manager.md 现有 3 万字规则（主脑提示词重写，目标几千字） |
| 项目授权（project_grants） | 历史表现统计页面（有用的结论并进模型档案） |

## 4. 分期

每期结束都用一次真实的小活实测，过了再进下一期。重构期间旧协作照常可用，直到第 3 期。

### 第 1 期：单个主脑跑通
- 新模块，不改旧调度代码。
- 主脑会话 + 独立对话界面 + 插话；派活 / 成员动态 / 问用户三个工具；成员交付回送主脑。
- 模型档案初稿 + 新的主脑提示词和成员说明。
- 实测：在一个项目里开一个主脑，让它完成一件需要派 2 个成员的小事（一个改代码、一个跑测试构建），中途插话改一次方向。
- 量：花了多少、有没有遗留、插话多久生效、杂活落在谁身上。

### 第 2 期：长活与多项目
- 任务书：主脑对长难的活先写任务书、边做边勾；中途换会话能读任务书接着做。
- 事的排队：做着一件时你提新事，排在后面；你让它先做新的，它停稳、记进任务书再换。
- 多个项目的主脑同时跑；查额度工具；同一成员 CLI 被多处使用时排队或并行。
- 项目群汇总视图。
- 实测：一个项目跑一件需要任务书的长活（中途插一件新事），同时另一个项目的主脑做一件小事。

### 第 3 期：删旧、发版
- 删除第 3.5 节右列的代码、表、提示词、前端页面和测试；数据库只做必要迁移，旧数据不再展示。
- 更新 README 和流程文档。
- 发版。

## 5. 风险

- **主脑质量决定一切。** 没有流程兜底，主脑偷懒就做不完。应对：主脑默认用强模型；提示词写清「对做完负责、不留遗留」；第 1 期实测重点看这个。
- **主脑上下文涨得快。** 读代码、看日志尽量交给成员；靠压缩；一件事一个会话。第 1 期实测成本，比现在贵就调整。
- **成员之间合并冲突。** 同一件事里并行的成员改到同一处时，由主脑合并时处理；拆活时尽量让并行的成员不碰同一批文件。
- **大改。** 旧调度大部分作废。用新模块并行开发、跑通后整块删除来控制风险，不在旧代码上边改边用。

## 6. 我（监视者）的做法

- 重构期间不再给旧调度打补丁，除非是阻断性 bug。
- 实测中发现的问题记进本目录的问题清单，按根因成批改，不当场插话改规则。
