### 用户

### 现状（Claude 核对的数）
- 10-15 以来 95 个提交：39 个 fix、43 个 feat，大多是「监视时撞到一个问题就补一条规则或一段分支」。
- 调度相关代码约 8600 行（project_coordinator 2428、coordinator_store 1193、coordinator_policy 864、project_native 1301、测试 2799）。
- 调度提示词 manager.md 约 3.1 万字、19 个【】小节；成员说明 member.md 约 4500 字。调度每回合都要带着这 3 万字。

### Claude 的判断：屎山是怎么长出来的
1. **补丁对着症状打，不对着模型打。** 每个补丁都只补一个洞，背后的机制没变：
   - 「成员空跑却算完成」→ 加了 undelivered 判定和同会话再交代；
   - 「失败要等下一回合」→ 加了 redo_request 小回合；
   - 「恢复后空分派」→ 加了空分派放行；
   - 「另开壳测试」→ 提示词再加一句。
   这些都对，但叠在一起就是一堆互相牵连的特例。
2. **调度靠「无状态回合 + 账本」，同席靠「代码里的流程」，两边在抢同一件事的控制权。** 什么时候派、什么时候合并、失败怎么办、能不能放行后续，一半写在 Rust 里（批次、依赖、hold_merge、软预算、当场重派），一半写在提示词里让调度判断。哪边说了算不清楚，所以每出一次乌龙就两边各补一刀。
3. **一回合一回合的「问—答—执行」开销太大。** 拨款、请教、重派、主回合都是独立的「问调度」调用，每次都重带参考资料和规则。规则越多越贵，也越容易让调度漏看某条。
4. **完成的定义太弱。** 「完成」= 成员进程正常退出；交付摘要、提交、验证结论都是事后猜。S7-c 的乌龙就出在这里。
5. **我（监视者）自己也是补丁来源。** 我插话、我临时改授权、我在协作中途改代码重启，这些本身就在制造特例（比如那次叫 Haiku「别替换生产」）。

### 可以讨论的方向（Claude 提出，待用户表态）
- **A. 做减法：** 先盘点现有规则和分支，按「这条规则在防什么」归类，合并或删掉重复的；给 manager.md 定一个体积上限。
- **B. 换控制模型：** 二选一，不再两边各管一半。
  - B1 同席只做执行器（开会话、跑任务、合并、报状态），所有决定交给一个**常驻的调度会话**（带上下文，不再每回合重读 3 万字规则），事件来了就推给它。
  - B2 反过来，流程写死在同席里（派→做→自检→合并→下一项），调度只在少数节点上做选择题（派给谁、要不要重做、要不要问用户）。
- **C. 把「完成」变成合同：** 每项任务派出时就写明交付物（提交 / 报告路径 / 部署 + 冒烟结果），同席按合同验收，验不过就是没完成，不靠猜。
- **D. 我的角色：** 监视时只记录问题、不当场补丁，攒到一批后按根因统一改，或者每次改动都先写进这份文件再动手。

### 需求（Claude 归纳，待用户确认）
1. **核心只有一个：** 主脑按需求把活分给合适的成员，能力和活相当，强模型不去干测试这类杂活。
2. **前提是能正常做完：** 像这个对话里一样，一件事一路做到完，不是做一截留一堆「未验证、未构建、遗留」。
3. **能及时指引方向：** 插话马上到主脑手里，不等下一轮。
4. **最心疼：** 同一个问题在「派人排查 → 修复 → 遗留 → 再派人排查」里打转。
5. 功能多到说不清，等于没有。

### Claude 的想法
**为什么这个对话里能做完，协作里做不完：**
- 这里是**一个会话从头到尾负责**：我一直带着上下文，查到哪改到哪，做完自己验一下，你随时插话我马上就改方向。
- 协作里是**流水线**：主脑每回合是新开的会话，只看账本和交付摘要；活被切成小项派给不带上下文的成员；成员按条文（不要 xxx、遗留分三档、需授权……）交差，交不完就写成遗留；主脑再从摘要里读到遗留，又派一个新人从头排查。你最心疼的那个循环就是这么来的——每一棒都没有完整的上下文，也没人对「这件事做完」负责。
- 那些「不要 xxx」「遗留 xxx」很多是我这些天为了堵某次乌龙加进提示词的。限制越多，成员越倾向于停在边界上交报告，而不是把事做完。

**Orca 开三个终端放手做，好在哪、差在哪：**
- 好：每个 agent 自己负责到底、上下文连续、你随时能对任何一个说话。这正是现在同席缺的。
- 差：没人分活，三个都按自己的模型跑（强模型照样去跑测试）；同一个工作树里三个人互相踩；谁负责收口不清楚。
- 所以老实说：**就「把活做完」这一点，Orca 那种做法现在确实比同席强。** 同席值得存在的唯一理由是你说的那条——按能力分活、省强模型额度——而现在这条被一层流水线机制压住了，没发挥出来。

**我建议的方向：把同席从「流程引擎」改成「一个主脑会话 + 一组成员工具」**
- 主脑就是一个常驻的会话（强模型），像这个对话里的我一样：带着上下文，自己对整件事负责到做完。
- 你在群里说话，直接进主脑的会话（马上插话，不等回合）。
- 同席给主脑几样工具：「把这件事交给某成员（指定模型）」、「看成员在干嘛 / 给成员插话」、「问用户」。成员做完把结果交回主脑，主脑自己判断够不够、要不要接着让同一个成员改，而不是记一条遗留。
- 主脑分活的原则就一条：贵的模型想、判断、收口；便宜的模型干体力活（跑测试、构建、查日志、批量改）。拿不准就自己看一眼。
- 成员说明只留最少的规矩（在哪个目录、做完交什么、别泄密），不再列禁区和遗留分档。
- 大部分现在的机制可以删：回合制、账本、拨款请求、当场重派、空跑判定、遗留池分档、验证门、软预算……额度和价格信息还给主脑看，让它自己掂量。
- 要留的：成员和模型目录、价格与额度信息、用量统计、每个成员的会话、问答面板（如果你还想要）、可选的工作树隔离。

**代价和风险：**
- 主脑一直开着，上下文会涨，要靠压缩或分段；但现在调度每回合重读 8.6 万、一周 $77，常驻会话靠缓存未必更贵，要实测。
- 主脑的质量决定一切：它偷懒，就没有流程兜底。但现在的流程兜底也没兜住。
- 这是大改：等于重写协作这一块，旧的调度代码大部分作废。

## 结论汇总
1. 需求（第 3 轮归纳）用户确认基本正确：主脑按能力分活、强模型不干杂活；前提是一件事能做完；插话即时到主脑；不在「排查—修复—遗留」里打转。
2. 方向：同席改为「主脑会话 + 成员工具」，不再是回合制流程引擎。
3. 成员各自有工作树，由主脑负责合并。
4. 主脑按项目分，不是全局一个；一件事一个主脑会话，靠项目的长期计划文件跨会话交接。
5. 一个项目只有一个主脑，事一件一件做；长难的活由主脑先写任务书（第 8 轮。第 5 轮记的「同项目多主脑」是 Claude 从问题里推出来的，已作废）。
6. 多个项目、多个主脑抢额度时不设优先级，各主脑看着全局额度自己让。
7. 每个主脑一个独立对话（像私聊一样点进去说），项目群里只显示汇总。
8. 主脑模型：项目里设默认，开新主脑时可改。
9. 删掉价格表自动更新、用量统计、额度显示；改为一份模型档案（能力档 + 贵贱档 + 擅长），让主脑清楚哪个强、哪个贵。保留问答面板和长期计划文件。
10. 方案 v0.2 的验收标准、保留 / 删除表、分期顺序，用户都认可（第 7 轮）。
